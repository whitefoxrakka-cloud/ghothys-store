ANTI-SPAM ORDER (sudah aktif, versi 2026-09-25)
  1. Header Sec-Fetch-Mode/Dest/Site wajib ada dan nilainya sesuai fetch()
     browser. Kalau ketiganya tidak ada, hanya Origin dari ALLOWED_ORIGINS
     yang diterima (browser lawas). curl/python/lynx = 403.
  2. Honeypot: field tersembunyi name="website" di #topup-form. Terisi = 400.
  3. Dwell time: klien kirim t = kapan form dibuka. < 2 detik = 400.
     t kosong/0 tetap diterima agar halaman lama di cache tidak rusak.
   4. Rate limit 5 order / 10 menit / IP (balas 429 + Retry-After).
      Klien otomatis coba lagi sekali setelah jeda 3,2 detik.
      Sekarang ada DUA lapis:
      a) Map di memori isolate (pembatas cepat, tidak menambah biaya).
      b) Durable Object "RateLimiter" (pembatas KERAS). Satu instance
         global, request-nya diproses satu per satu, dan hitungannya
         disimpan di storage DO dengan masa berlaku 10 menit, jadi
         tetap berlaku walau instance di-evict atau Worker di-deploy
         ulang. Bukti 25/09/2026: 12 request paralel -> tepat 5x 200
         dan 7x 429 (sebelumnya 10 paralel -> hanya 1x 429).
         Kalau DO tidak bisa dihubungi, sistem JALAN (fail-open)
         supaya order asli tidak terlambat.
      Batas paket free: Durable Object WAJIB dibuat lewat migrasi
      new_sqlite_classes (new_classes ditolak dengan kode 10097).
      Login admin juga memakai DO yang sama: 8 percobaan / 10 menit /
      (ip+email), lalu 429. Bukti: 8x 401 lalu 429.
   5. Cek duplikat Order ID di Airtable (balas 200 duplicate, tidak kirim
      ulang ke Discord/Telegram).
   6. Validasi ketat: order_id /^INV-\d{8}-\d{1,6}$/, game & uid wajib,
      price 1-5.000.000, panjang tiap field dibatasi.
   7. Harga dinormalisasi: "Rp 10.000" (kiriman versi lama) dibaca 10000,
      bukan 10. Tanpa ini kolom Price di Airtable korup.
   CATATAN: ini menahan spam/bot, bukan otentikasi. Kalau butuh proteksi
   lebih ketat (mis. wajib login/OTP), itu perubahan terpisah.
   Lapis WAF di dashboard Cloudflare masih opsional kalau
   kamu mau menahan traffic yang tidak pernah sampai ke Worker.

  CARA MENYIMPAN (dipakai sehari-hari)
    1. Buka https://<nama-toko>.github.io/ lalu masuk ke panel owner.

  CARA KERJA LOGINNYA
    Login menulis cookie ghothys_admin (HttpOnly, Secure, SameSite=None)
    di domain worker. Cookie tidak bisa dibaca JavaScript jadi aman dari
    pencurian lewat XSS. Halaman toko memakai cookie itu lewat
    fetch(credentials:"include"); panel /admin/ tetap memakai header
    Bearer dari sessionStorage seperti sebelumnya. Server menerima
    keduanya, jadi salah satu diblokir peramban tidak mematikan semua.
    Kalau peramban memblokir cookie pihak ketiga, kotak login muncul
    lagi - tidak merusak data.

  CARA MEMULIHKAN (butuh kamu, karena isinya data kamu)
    1. Buka situs di browser yang biasa kamu pakai untuk edit konten
       (browser dengan localStorage yang masih ada isinya).
       Kalau localStorage sudah kosong, isi tidak bisa dipulihkan -
       harus diketik ulang dari panel owner.
    2. Di panel owner, login sekali lewat kotak Sinkronisasi Konten
       (tidak perlu pindah tab, tidak perlu /admin/login.html lagi).
    3. Cek isi pengumuman/event/banner, lalu klik Simpan.
    4. Toast hijau "Konten tersimpan" = berhasil. Verifikasi:
       buka https://<worker>.workers.dev/content
       isi announcements/events/banners harus muncul.
    5. Kalau toast merah "Server menolak" dengan 409, berarti kamu
       sengaja menghapus semua - klik Simpan lagi setelah memastikan.

ROTASI PASSWORD ADMIN
  25/09/2026 password admin sudah dirotasi karena sebelumnya ada plaintext
  di backend/scripts/seed-admin.js. File itu sekarang membaca password dari
  environment variable ADMIN_PASSWORD dan tidak bisa jalan tanpa itu.
  Kabar baik: folder backend/ TIDAK pernah masuk repository GitHub
  (sudah dicek dengan git log -S, tidak ada jejaknya), jadi password lama
  tidak bocor lewat riwayat commit. Repo ini hanya berisi file statis
  GitHub Pages. Tetap verdict lama tidak dipakai lagi di mana pun.

  Cara rotasi (jangan print password ke terminal/chat):
   1. Buat password + hash di file temp, bukan di layar:
      node -e "const c=require('crypto'),fs=require('fs');\
       const set='abcdefghijkmnopqrstuvwxyzABCDEFGHJKLMNPQRSTUVWXYZ23456789!@#$%';\
       const pw=Array.from(c.randomBytes(22)).map(b=>set[b%set.length]).join('');\
       const s=c.randomBytes(16),h=c.pbkdf2Sync(Buffer.from(pw),s,60000,32,'sha256');\
       const b=x=>x.toString('base64').replace(/\+/g,'-').replace(/\//g,'_').replace(/=+$/,'');\
       fs.writeFileSync(process.env.TEMP+'/hash.txt','pbkdf2$60000$'+b(s)+'$'+b(h));\
       fs.writeFileSync(process.env.TEMP+'/pw.txt',pw);"
   2. Pasang hash (JALANKAN DARI FOLDER relay/):
        npx wrangler secret bulk <file-json-berisi>{"ADMIN_PASSWORD_HASH":"..."}
      Catatan: di Windows "npx wrangler secret put X" lewat pipe stdin bisa
      crash (Assertion failed UV_HANDLE_CLOSING) dan diam-diam tidak memasang
      apa pun. Pakai "secret bulk" dengan file JSON, lalu WAJIB tes login.
   3. Tes: password baru -> 200, password lama -> 401.
   4. Salin password baru ke clipboard untuk owner (Get-Content pw.txt |
      Set-Clipboard), jangan dicetak di chat.
   5. Kalau mengganti email admin juga: hash/plain lewat "secret bulk" dengan
      key ADMIN_EMAIL.
  PENTING: Cloudflare membatasi iterasi PBKDF2 maksimal 100.000. Di atas itu
  verifyPassword selalu gagal (login selalu 401) walau hash-nya benar.
